# Human Test Checklist: versioned builds in one fixed folder (#3)

**Target version:** 0.1.5
**Ships with commit:** v0.1.5: versioned builds in one fixed folder (#3)
**Companion automated tests:** 63 in the suite; the 15 tests for this feature are the `apply` tests in `tests/test_cli.py`. Mutation sweep: 22 of 22 killed over two rounds (`tests/mutation/v0.1.5__sweep__builds.md`).

## What this is

`apply` without `-o` now writes each build under both versions' names, into one builds folder whatever folder it is run from. It points `claude-dcc.exe` there at the newest build, and refuses to write inside Claude Code's own config folder. This checklist covers what the automated tests stub out: the real Windows "exe in use" refusal, hardlinks on a real NTFS volume, and the path forms each shell produces. djdarcy runs it.

## Prerequisites

1. Windows, Claude Code's native build at `%USERPROFILE%\.local\bin\claude.exe`. Commands run from the repository root unless a step says otherwise.
2. **A scratch builds folder** keeps every test below away from your real builds. Set it in each terminal you use:
   - **cmd.exe:** `set DCC_BUILDS_DIR=%TEMP%\dcc-builds-test`
   - **PowerShell:** `$env:DCC_BUILDS_DIR = "$env:TEMP\dcc-builds-test"`
   - **POSIX (Git Bash):** `export DCC_BUILDS_DIR="$TEMP/dcc-builds-test"`
3. Section 2 runs a patched build. Run it in the test config (`python scripts/test_config.py env` prints the two variables), never in a real session.

**Reset between sections:** delete the scratch folder.
- **cmd.exe:** `if exist %TEMP%\dcc-builds-test rmdir /s /q %TEMP%\dcc-builds-test`
- **PowerShell:** `if (Test-Path $env:TEMP\dcc-builds-test) { Remove-Item -Recurse -Force $env:TEMP\dcc-builds-test }`
- **POSIX:** `rm -rf "$TEMP/dcc-builds-test"`

## High-Value Verification (~5 minutes)

### HV.1 -- a build gets both versions' names, from any folder

- [ ] **Steps:** `cd %USERPROFILE%` (PowerShell `cd $env:USERPROFILE`, POSIX `cd ~`), then `dcc-patcher apply %USERPROFILE%\.local\bin\claude.exe` (PowerShell `$env:USERPROFILE\...`, POSIX `~/.local/bin/claude.exe`).
- [ ] **Expected:** every patch `applies`; then `wrote <TEMP>\dcc-builds-test\claude-dcc-<claude>+dcc0.1.5.exe`, `and <same>.dcc-lock.json`, and `<TEMP>\dcc-builds-test\claude-dcc.exe -> claude-dcc-<claude>+dcc0.1.5.exe (hardlink)`; exit 0. All paths are absolute, and nothing is written in the home folder.
- [ ] **Why this matters:** a build that lands where it was run from (`~/.claude` once received 258 MB) is the bug this fixes.

### HV.2 -- rebuilding says "already built"

- [ ] **Steps:** run the same `apply` again.
- [ ] **Expected:** `already built: <path>`, the `claude-dcc.exe` line, exit 0. The folder still holds exactly three files.
- [ ] **Why this matters:** the launcher will call `apply` on every update; a no-op must be cheap and quiet.

### HV.3 -- the link is a real hardlink

- [ ] **Steps:** `fsutil hardlink list %TEMP%\dcc-builds-test\claude-dcc.exe` (cmd or PowerShell; POSIX: `ls -l "$TEMP/dcc-builds-test"`, where the link count shows `2`).
- [ ] **Expected:** both names are listed (or a link count of 2), and the folder's size is one build, not two.

### HV.4 -- `~/.claude` is refused

- [ ] **Steps:** `cd %USERPROFILE%\.claude`, then `dcc-patcher apply %USERPROFILE%\.local\bin\claude.exe -o build-out\claude-dcc.exe`.
- [ ] **Expected:** `dcc-patcher: refusing to write inside Claude Code's config folder (...\.claude): ...\.claude\build-out\claude-dcc.exe`, exit 2, and no `build-out` folder created.

## Section 2: a build in use (Windows)

### 2.1 -- `claude-dcc.exe` running

- [ ] **Steps:**
  1. After HV.1, in a second terminal with the test config variables set, start `%TEMP%\dcc-builds-test\claude-dcc.exe` and leave it running.
  2. In the first terminal, run the HV.1 `apply` again.
- [ ] **Expected:** `already built: ...`, then one line, `dcc-patcher: the current build is in use, so it still points at the old one; the new build is at <path>`, with no traceback and exit 1. No `.dcc-*.tmp` file is left in the folder.
- [ ] **Then:** quit the running build and run `apply` again: exit 0, with the link line.

## Section 3: other shells and `-o`

### 3.1 -- `CLAUDE_CONFIG_DIR` is refused too

- [ ] **Steps:** set `CLAUDE_CONFIG_DIR` to the test config folder (cmd `set CLAUDE_CONFIG_DIR=%LOCALAPPDATA%\dazzle-claude-code-patcher\test-config`, PowerShell `$env:CLAUDE_CONFIG_DIR = ...`, POSIX `export CLAUDE_CONFIG_DIR=...`), then `dcc-patcher apply <claude.exe> -o %LOCALAPPDATA%\dazzle-claude-code-patcher\test-config\x.exe`.
- [ ] **Expected:** the refusal names that folder; exit 2; no `x.exe`.

### 3.2 -- `-o` writes exactly the file it names

- [ ] **Steps:** `dcc-patcher apply <claude.exe> -o %TEMP%\dcc-o-test\out.exe`, twice.
- [ ] **Expected:** `wrote <absolute path>` both times; no `claude-dcc.exe` beside it; nothing added to the scratch builds folder.

### 3.3 -- no `DCC_BUILDS_DIR`

- [ ] **Steps:** unset it (cmd `set DCC_BUILDS_DIR=`, PowerShell `Remove-Item Env:\DCC_BUILDS_DIR`, POSIX `unset DCC_BUILDS_DIR`), then run `dcc-patcher apply <claude.exe>` from any folder.
- [ ] **Expected:** from this checkout, the build goes to the repository's `private\builds\`. That is the real builds folder, so expect `already built` if it already holds this pair of versions.

## What the automated tests DON'T cover

- Windows' real refusal to replace a running exe (the tests stub `os.replace`).
- Hardlinks on a real NTFS volume, and a volume without them (stubbed `os.link`).
- How each shell expands `%USERPROFILE%`, `$env:USERPROFILE` and `~`.
- Whether the messages read clearly.

## Cleanup

Delete the scratch folders (`%TEMP%\dcc-builds-test`, `%TEMP%\dcc-o-test`) as in the reset step, and unset `DCC_BUILDS_DIR` and `CLAUDE_CONFIG_DIR`.
