# Human Test Checklist: the switch (`dcc-env <mode>`, `dazzle-claude`, `claude-stock`)

**Target version:** v0.2.1
**Ships with commit:** v0.2.1: the switch
**Companion automated tests:** 127 in the suite. New for this version: `tests/test_switch.py` (4) and `tests/test_launcher.py` (2 new, 1 updated). Red-green: all 7 fail under the revert of the behaviour each covers (`tests/one-offs/redgreen_v0.2.1.py`).

## What this is

v0.2.1 lets you change what `claude` means in the shell you're in (`dcc-env stock | patched | <build> | default`), adds `dazzle-claude` beside the renamed `claude-stock` so both builds always have a name, and makes `status` say which choice wins and why. The automated tests cover the Python behind it: the shim writer, the launcher's reading of `DCC_MODE`, the status line, the migration check. They cannot run the three `dcc-env` scripts in real shells, which is the whole feature; a person does that here, on a machine that already has a v0.2.0 (or older) install, since the first `dcc-env` migrates it.

## Prerequisites

1. Windows, with an existing install of dcc-patcher v0.2.0 or earlier set up (`claude` is the shim; `claude-stock` exists in `<builds>\bin` and `~/bin`). A fresh install also works; HV.1 then shows the three names written rather than renamed.
2. v0.2.1 installed: `pip install -e .` in a checkout, or the wheel.
3. Three shells to hand: cmd, PowerShell, Git Bash. Each step gives all three forms.
4. **State isolation:** nothing here touches `~/.claude` or any session file. The only changes are the shim files in the builds folder and `~/bin`, `launcher.json`, and the `DCC_MODE` variable of the shell you type in. `dcc-env default` clears the variable; `dcc-patcher use patched` restores the persistent default. No `PATH` change happens in this checklist (the entry already exists).
5. Note the builds folder: `dcc-patcher use` prints it (`builds:` line).

## High-Value Verification (~5 minutes)

**If you only have 5 minutes**, run these six. They are the feature.

### HV.1 — The first `dcc-env` adds `dazzle-claude` to an existing install

Validates: `install-shim --if-needed` treats a layout without `dazzle-claude` as not set up and writes the three names (the existing two rewritten in place).

- [ ] **Steps** (pick your shell; an already-open window is fine):

  **cmd.exe**:
  ```cmd
  dcc-env
  where claude
  dir /b "<builds>\bin"
  ```

  **PowerShell**:
  ```powershell
  dcc-env
  Get-Command claude, dazzle-claude, claude-stock -All | Select-Object Name, Source
  Get-ChildItem "<builds>\bin" | Select-Object Name
  ```

  **POSIX (Git Bash)**:
  ```bash
  . dcc-env
  which -a claude dazzle-claude claude-stock
  ls ~/bin
  ```
- [ ] **Expected:** `dcc-env` prints six `wrote ...` lines: `claude.cmd`, `claude-stock.cmd`, `dazzle-claude.cmd` in the bin folder and `claude`, `claude-stock`, `dazzle-claude` under `~/bin` (the first two of each trio rewritten in place). `where` / `Get-Command` / `which -a` find all three names. The last line is the brief status: `[x] claude -> ...\bin\claude.cmd` with `(the dcc-patcher shim; runs claude-dcc-<...>.exe (persistent: dcc-patcher use patched))`.
- [ ] **Why this matters:** without the migration, an existing install never gets `dazzle-claude`.

### HV.2 — `dcc-env stock` switches this shell; `dcc-env default` switches back

Validates: the mode argument sets `DCC_MODE` in the calling shell (no `setlocal` in cmd; process-wide `$env:` in PowerShell; sourced `$1` in sh), the launcher honours it, and `default` clears it.

- [ ] **Steps:**

  **cmd.exe**:
  ```cmd
  dcc-env stock
  claude --version
  echo %DCC_MODE%
  dcc-env default
  claude --version
  echo %DCC_MODE%
  ```

  **PowerShell**:
  ```powershell
  dcc-env stock
  claude --version
  $env:DCC_MODE
  dcc-env default
  claude --version
  $env:DCC_MODE
  ```

  **POSIX (Git Bash)**:
  ```bash
  . dcc-env stock
  claude --version
  echo "$DCC_MODE"
  . dcc-env default
  claude --version
  echo "$DCC_MODE"
  ```
- [ ] **Expected:** after `stock`, the brief line reads `runs stock (this shell: dcc-env stock; persistent: patched)` and `claude --version` prints the plain Claude Code version (no `dcc`, no `Dazzle`); `DCC_MODE` is `stock`. After `default`, the brief line reads `runs claude-dcc-<...>.exe (persistent: dcc-patcher use patched)`, `--version` reads `<version> + dcc 0.2.1 (Dazzle Claude Code)`, and `DCC_MODE` is empty (cmd prints `%DCC_MODE%` literally).
- [ ] **Why this matters:** this is the switch. If the variable doesn't survive the script, nothing else in the feature works.

### HV.3 — `dazzle-claude` and `claude-stock` ignore the mode

Validates: the two explicit shims carry their own `DCC_MODE` and run the same build whatever `claude` means.

- [ ] **Steps** (same in every shell; in Git Bash use `. dcc-env stock`):
  ```
  dcc-env stock
  dazzle-claude --version
  claude-stock --version
  dcc-env patched
  dazzle-claude --version
  claude-stock --version
  dcc-env default
  ```
- [ ] **Expected:** `dazzle-claude --version` always shows `+ dcc 0.2.1 (Dazzle Claude Code)`; `claude-stock --version` never does; the mode set by `dcc-env` changes neither.
- [ ] **Why this matters:** the explicit names are the escape hatch when `claude` is set the other way.

### HV.4 — A new window starts from the persistent choice

Validates: the per-shell switch is per shell.

- [ ] **Steps:** in one window run `dcc-env stock` (Git Bash: `. dcc-env stock`). Open a **new** window of the same shell. In it:

  **cmd.exe**: `claude --version` then `echo %DCC_MODE%`
  **PowerShell**: `claude --version` then `$env:DCC_MODE`
  **POSIX**: `claude --version` then `echo "$DCC_MODE"`
- [ ] **Expected:** the new window runs the patched build and has no `DCC_MODE`. The first window still runs stock until `dcc-env default` there.
- [ ] **Why this matters:** a switch that leaked into new windows would be `dcc-patcher use` by accident.

### HV.5 — A build's file name pins; a wrong word is named and ignored

Validates: `launch.valid_mode` accepts a build file name; anything else produces the one-line note and falls back to the persistent choice; `status --brief` says so.

- [ ] **Steps** (same in every shell; `<build>` is a file name from `dir "<builds>"`, e.g. `claude-dcc-2.1.294+dcc0.1.10.exe`):
  ```
  dcc-env <build>
  claude --version
  dcc-env stok
  claude --version
  dcc-env default
  ```
- [ ] **Expected:** after `<build>`, the brief line reads `runs the pinned build <build> (this shell: dcc-env <build>; persistent: patched)` and `--version` shows that build's versions. After `stok`, the brief line reads `...; this shell's DCC_MODE=stok is not stock, patched or a build and is ignored`, and `claude --version` prints `dcc: DCC_MODE=stok is not stock, patched or a build; using "patched"` on stderr, then the patched version.
- [ ] **Why this matters:** a typo must not silently run something else.

### HV.6 — `uninstall-shim` removes all three names; `dcc-env` puts them back

Validates: uninstall knows the new names and the old one; the round trip restores everything.

- [ ] **Steps** (same in every shell; Git Bash: `. dcc-env` at the end):
  ```
  dcc-patcher uninstall-shim
  dir "<builds>\bin"           (PowerShell: Get-ChildItem; Git Bash: ls ~/bin)
  dcc-env
  ```
- [ ] **Expected:** uninstall prints `removed ~/bin/claude`, `.../claude-stock`, `.../dazzle-claude` (and `.../claude-stock` if one of ours was still there), removes the user `PATH` entry (with a backup line first), and leaves the `.cmd` shims in the builds folder, as documented. `dcc-env` then writes and re-adds everything, and the brief line is green again.
- [ ] **Why this matters:** an uninstall that leaves a shim behind is a file nobody can explain later.

## Section 1: Shell syntax and fallbacks (~5 min)

### 1.1 PowerShell with scripts disallowed

- [ ] **Steps:** in a PowerShell with `Get-ExecutionPolicy` reading `Restricted` (or `Set-ExecutionPolicy -Scope Process Restricted` in a throwaway window):
  ```powershell
  dcc-env stock
  dcc-patcher shellenv powershell | Invoke-Expression
  $env:DCC_MODE = 'stock'
  claude --version
  Remove-Item Env:\DCC_MODE
  ```
- [ ] **Expected:** `dcc-env` is refused by PowerShell's policy (the error names the policy). The `shellenv | Invoke-Expression` line puts the folder on `PATH`; it does **not** take a mode, so the variable is set by hand, after which `claude` runs stock.
- [ ] **Check:** `dcc-patcher status` (full) shows the fallback line under "This shell" when the policy blocks scripts.

### 1.2 Git Bash: run, not sourced

- [ ] **Steps:**
  ```bash
  dcc-env stock
  echo "$DCC_MODE"
  ```
- [ ] **Expected:** run as a command (not `. dcc-env`), the script's `export` lands in a child shell and `DCC_MODE` stays empty in yours. The comment at the top of `dcc-env` says to source it; the brief line it prints is from the child.

### 1.3 A PowerShell opened from Git Bash (seen live, 2026-10-09)

Git Bash puts `~/bin` first on its PATH; a PowerShell started from it inherits that, and then resolves `claude-stock` to the extensionless sh script in `~/bin` and hands it to Windows ("How do you want to open this file?").

- [ ] **Steps:** in Git Bash, run `powershell` (or `pwsh`). In that PowerShell:
  ```powershell
  (Get-Command claude-stock -All).Source
  dcc-patcher status
  dcc-env
  (Get-Command claude-stock -All).Source
  claude-stock --version
  ```
- [ ] **Expected:** before `dcc-env`, the first `Source` is `C:\Users\<you>\bin\claude-stock` and `status` shows `[!] C:\Users\<you>\bin is ahead of the shims on this shell's PATH` with `-> dcc-env`. After `dcc-env`, the first `Source` is `...\builds\bin\claude-stock.cmd`, the row is gone, and `claude-stock --version` prints the stock version with no dialog.

### 1.4 Case and spaces

- [ ] **Steps:** `dcc-env Default` (cmd), `dcc-env DEFAULT` (PowerShell), `. dcc-env default` (sh).
- [ ] **Expected:** cmd and PowerShell treat `default` case-insensitively (the `if /i` and `-eq`); sh is case-sensitive, by design of the shell. A mode with a space can't be a build name and is named and ignored.

## Section 2: Precedence (~3 min)

### 2.1 This shell beats the persistent choice

- [ ] **Steps:**
  ```
  dcc-patcher use stock
  dcc-env patched
  claude --version
  dcc-env default
  claude --version
  dcc-patcher use patched
  ```
- [ ] **Expected:** with `use stock` persistent and `dcc-env patched` in the shell, `claude` runs the patched build and the brief line reads `(this shell: dcc-env patched; persistent: stock)`. After `default`, it runs stock. After `use patched`, patched again.

### 2.2 A pinned build in both places

- [ ] **Steps:** `dcc-patcher use <build A>` then `dcc-env <build B>` then `claude --version`, then `dcc-env default`, `dcc-patcher use patched`.
- [ ] **Expected:** build B runs in this shell; `dcc-patcher use` (no argument) still shows `mode: <build A>`.

### 2.3 Test config: no rebuild

- [ ] **Steps:** with `CLAUDE_CONFIG_DIR` set to a scratch folder, `dcc-env patched` then `claude --version`.
- [ ] **Expected:** no rebuild happens in a test config (the launcher says so if one would be needed); the mode still applies.

## Section 3: Files the tool must not touch (~2 min)

### 3.1 A shim-named file that isn't ours survives

- [ ] **Steps:**

  **cmd.exe**:
  ```cmd
  echo #!/bin/sh> "%USERPROFILE%\bin\claude-stock"
  dcc-env
  type "%USERPROFILE%\bin\claude-stock"
  del "%USERPROFILE%\bin\claude-stock"
  ```

  **PowerShell**:
  ```powershell
  Set-Content "$HOME\bin\claude-stock" "#!/bin/sh"
  dcc-env
  Get-Content "$HOME\bin\claude-stock"
  Remove-Item "$HOME\bin\claude-stock"
  ```

  **POSIX**:
  ```bash
  printf '#!/bin/sh\n' > ~/bin/claude-stock
  . dcc-env
  cat ~/bin/claude-stock
  rm -f ~/bin/claude-stock
  ```
- [ ] **Expected:** `dcc-env` says `~/bin/claude-stock exists and isn't one of ours; left it alone` (no marker line) and the file's content is unchanged; the other shims are written as usual. The same holds for a `dazzle-claude` or `claude` of your own.

## Section 4: `status` (~2 min)

### 4.1 The rows and the note

- [ ] **Steps:** `dcc-patcher status` with no `DCC_MODE`, then with `dcc-env stock`, then `dcc-env default`.
- [ ] **Expected:** under "This shell": the `claude` row's note ends `(persistent: dcc-patcher use patched)`, then `(this shell: dcc-env stock; persistent: patched)`; two rows `[x] claude-stock -> ...` and `[x] dazzle-claude -> ...` with their paths in the brighter shade. In a shell without the shim folder on `PATH`, the two rows are `[ ]` with `-> dcc-env` as the fix, and the exit code is 1.

## What the automated tests DON'T cover

- **The three `dcc-env` scripts themselves**: the cmd `if` block running without `setlocal`, PowerShell's `param` binding and `$env:` scope, the sourced sh script's `$1`. Only a real shell shows whether the variable outlives the script.
- **PATH order in real shells** (which of three names wins, in each shell, from the Start menu).
- **The live migration** of an existing install, including a Git Bash `~/bin` the user has added to.
- **Rendering** of the longer brief line in a narrow window.
- **The error message** for a wrong word, as a user reads it.
