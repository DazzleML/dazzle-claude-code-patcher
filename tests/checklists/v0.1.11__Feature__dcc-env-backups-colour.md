# Human Test Checklist: dcc-env, PATH backups, Git Bash shims in ~/bin, colour

**Target version:** 0.1.11
**Ships with commit:** TBD (v0.1.11)
**Companion automated tests:** 118 in total. New in this version: `tests/test_path_backups.py` (10, on a fake registry), plus updates in `tests/test_launcher.py`, `tests/test_path.py` and `tests/test_packaging.py`. Red-green: all 16 new behaviours are anchors (`tests/one-offs/redgreen_v0.1.11.py`). The `.reg` format was checked against the real `reg.exe` on a scratch key (`tests/one-offs/thinking/user-path-editor/regfile_roundtrip.py`).

## What this is

These checks need a real shell, a real registry and a real reinstall. In particular: whether `dcc-env` brings a shell that was open before the install up to date, whether the move of the Git Bash shims fixes claude-session-backup's `resume`, and whether colour and the restore read well.

## Prerequisites

1. **dcc-patcher 0.1.11 reinstalled,** so pip puts `dcc-env` beside `dcc-patcher`: `pip install -e .` from the repository (or `pip install .`). Check it's there:
   - cmd: `where dcc-env`
   - PowerShell: `Get-Command dcc-env -All`
   - Git Bash: `type -a dcc-env`
2. **A shell that was open before v0.1.10's `install-shim`,** or any shell where `dcc-patcher status` shows `[!] ... this shell started before the PATH change`.
3. **Back up the user environment** (the same command as in v0.1.10's checklist): `reg export HKCU\Environment "%TEMP%\dcc-env-backup-0.1.11.reg" /y` (cmd) or `reg export HKCU\Environment "$env:TEMP\dcc-env-backup-0.1.11.reg" /y` (PowerShell).

## High-Value Verification (~10 minutes)

### HV.1 -- `dcc-env` in an old cmd window

- [ ] **Steps:** in a cmd window opened before the install, run:
  1. `dcc-patcher status`
  2. `dcc-env`
  3. `claude --version`
- [ ] **Expected:**
  - Step 1 shows `[!] claude -> ...\.local\bin\claude.exe (stock): this shell started before the PATH change` with `-> dcc-env`. On a machine still in the v0.1.10 layout, it also shows `[!] ...\builds\bin\claude is an sh script on the Windows PATH`.
  - Step 2 prints `removed ...\builds\bin\claude` and `...\claude-stock` (the old layout only), then `wrote C:\Users\<you>\bin\claude` and `...\claude-stock`, `user PATH: already has ...`, and one `[x] claude -> ...\builds\bin\claude.cmd ...` line.
  - Step 3 prints `<version> + dcc 0.1.11 (Dazzle Claude Code)`.
- [ ] **Why this matters:** this is the "fix the shell I'm in" command. Users won't restart every shell.

### HV.2 -- `dcc-env` in an old PowerShell

- [ ] **Steps:** in a PowerShell opened before the install: `dcc-env`, then `claude --version`.
- [ ] **Expected:** one `[x] claude -> ...claude.cmd` line, then the dcc version. If the execution policy blocks scripts, PowerShell refuses to run `dcc-env.ps1`; then `dcc-patcher shellenv powershell | Invoke-Expression` does the same, and `status` suggests it.

### HV.3 -- Git Bash finds the shim in `~/bin`

- [ ] **Steps:**
  1. Open a **new** Git Bash.
  2. `type -a claude`, then `claude --version`.
  3. In an older Git Bash: `. dcc-env`, then `type -a claude`.
- [ ] **Expected:** `claude is /c/Users/<you>/bin/claude` comes first and the version line has the dcc label. `<builds>/bin` holds only `claude.cmd` and `claude-stock.cmd`.

### HV.4 -- claude-session-backup's `resume` works again

- [ ] **Steps:** `csb resume last` (or whichever `csb resume` failed with `WinError 193`).
- [ ] **Expected:** no "not a valid Win32 application". Python 3.12.0's `shutil.which('claude')` now finds `claude.cmd`. Check it with:
  ```
  python -c "import shutil; print(shutil.which('claude'))"
  ```
  It should print `...\builds\bin\claude.CMD` (any case).

### HV.5 -- a backup, and putting it back

- [ ] **Steps:**
  1. `dir <builds>\backups` (cmd) / `Get-ChildItem <builds>\backups` (PowerShell) / `ls <builds>/backups` (Git Bash). There should be one `<date>__<time>__path-user__before-...reg` per PATH change.
  2. `dcc-patcher uninstall-shim`, then `dcc-patcher restore-path`, and answer `y`.
- [ ] **Expected:**
  - `uninstall-shim` prints `saved the user PATH first: ...before-uninstall-shim...reg`.
  - `restore-path` lists `+ <builds>\bin` and asks, then says `user PATH restored; the value it replaced is saved as ...before-restore-path...reg`.
  - `dcc-patcher status` shows `[x] user PATH has ...` again.
  - Opening one backup in Notepad shows only `[HKEY_CURRENT_USER\Environment]` and `"Path"=...`, nothing else.

### HV.6 -- colour

- [ ] **Steps:** `dcc-patcher status` in cmd, PowerShell, Windows Terminal and Git Bash. Then `dcc-patcher status | more` (cmd), `dcc-patcher status | Out-Host` (PowerShell) or `dcc-patcher status | cat` (Git Bash). Then the same with `NO_COLOR` set: `set NO_COLOR=1` / `$env:NO_COLOR = "1"` / `export NO_COLOR=1`.
- [ ] **Expected:**
  - in a terminal: section headings bold, `[x]` green, `[ ]` yellow, `[!]` red, fix commands cyan, detail dim;
  - piped, or with `NO_COLOR`: plain text with no escape codes.
- [ ] **Check:** is it readable in every one, including plain `conhost` cmd windows?

## What the automated tests DON'T cover

- `reg.exe` itself. The one-off above checked it once; the suite never calls it.
- pip's real install of `dcc-env` into Scripts, for editable and normal installs. The suite checks the wheel's contents only.
- Which `dcc-env` PowerShell chooses (`.ps1` was first here) and how the execution policy behaves.
- Git for Windows' `~/bin` rule on another machine or Git version.
- csb itself.
- How the colours look.

## Cleanup

- `dcc-patcher restore-path <file>` for any backup in `<builds>\backups`.
- Or, for the whole user environment: `reg import "%TEMP%\dcc-env-backup-0.1.11.reg"`, then sign out and in.
- `~/bin\claude` and `~/bin\claude-stock` can be deleted if Git Bash isn't used. `status` then shows `[~] Git Bash: no shim`.
