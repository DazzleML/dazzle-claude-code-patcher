# Human Test Checklist: grouped `dcc-patcher -h`, `dcc-patcher update`, `dcc-env -h/-V`

**Target version:** 0.2.4
**Ships with commit:** v0.2.4 (TBD)
**Companion automated tests:** 188 in the suite; new in v0.2.4: `tests/test_verbs_update.py` (38: grouped help, every invocation still parses, the launcher never loads dazzle-lib, the fallback without it, the offline check, every guard in front of pip, the stamp) and `tests/test_switch.py` (+18: `dcc-env -h/--help`, a refused `-option`, `-V/--version`, in cmd, PowerShell and Git Bash against a stub dcc-patcher). Red-green: `tests/one-offs/redgreen_v0.2.4.py` (22 mutants, each red, each restored).

## What this is

What a person has to look at for v0.2.4: the help as it reads in a real terminal, `dcc-env` in each real shell, and `update --fix` running real pip from the running `dcc-patcher.exe` on Windows, where pip reports an error even though the update completes.

## Prerequisites

1. Windows, Python 3.11+, this checkout installed editable (`pip install -e .`) or the 0.2.4 wheel installed.
2. Nothing here writes to your PATH or registry. HV.4 runs pip on your Python; it is the same `pip install -e .` you would run by hand.

## High-Value Verification (~5 minutes)

### HV.1 -- the grouped help

- [ ] **Steps** (any shell): `dcc-patcher -h`
- [ ] **Expected:** `usage: dcc-patcher [-h] [-V] <command> ...`, then three groups: `patches:` (inspect, validate, check), `builds:` (apply, use, rollback, archive), `this machine:` with the heading `install-shim <-> uninstall-shim; restore-path undoes PATH` (status, update, install-shim, uninstall-shim, restore-path, shellenv), then `options:`. No line runs past 80 columns; wrapped text lines up under its column.
- [ ] **Why this matters:** this is the screen the release is for; it should read as a map.

### HV.2 -- every old command line still works

- [ ] **Steps:** `dcc-env` (in cmd or PowerShell), then `dcc-patcher status --brief`, `dcc-patcher use`, `dcc-patcher shellenv cmd --folder`
- [ ] **Expected:** the same output as under 0.2.3 (plus, at most, the update line from HV.3).
- [ ] **Why this matters:** dcc-env and the docs call these; the grouping must change reading only.

### HV.3 -- `update` names a stale editable install

- [ ] **Steps:** before reinstalling (the Scripts copies are older than the checkout): `dcc-patcher update`, then `dcc-patcher status`, then `dcc-env`
- [ ] **Expected:** `update` lists the three Scripts copies `[!]`, `PyPI: 0.2.3 is the latest release (...)` (or `not reached (...)` offline), two `waiting:` lines (the dcc-env scripts; `pip records 0.2.3; the checkout is 0.2.4`) and `-> dcc-patcher update --fix   (runs: ...python.exe -m pip install -e <checkout>)`; exit code 1. `status` has an `Updates` group with the same two lines and one `-> dcc-patcher update --fix`. `dcc-env`'s line gains one row naming the scripts and the fix.
- [ ] **Why this matters:** this is the staleness that went unnoticed for two releases.

### HV.4 -- `update --fix`, the Windows way

Make the install stale first (edit a comment in `bin\dcc-env.cmd` in the clone, or test before reinstalling).

- [ ] **Steps:** `dcc-patcher update --fix --dry-run` (shows the command, runs nothing); `dcc-patcher update --fix` (refuses: `dcc-patcher.exe can't update itself...` and names `<python> -m dcc_patcher update --fix`, exit 2, pip not run); then the named command, press Enter (expect `nothing changed`); then the named command again, answer `y`
- [ ] **Expected:** pip runs, then `done.` and `The next \`claude\` start rebuilds if the dcc-patcher version changed.` Afterwards `dcc-patcher update --offline` says `up to date`; `claude` and `dcc-patcher -V` both still start.
- [ ] **Why this matters:** on 2026-10-09 pip, run from the running `dcc-patcher.exe`, failed on the locked exe (WinError 32) halfway through and left dcc-patcher uninstalled; `claude` couldn't start until a reinstall from `python.exe`. This step proves the route that works and the refusal that prevents the other.

### HV.5 -- `dcc-env -V` and `-h` in each shell

- [ ] **Steps** (each shell):

  **cmd.exe**: `dcc-env -V` then `dcc-env --help` then `dcc-env --stock`
  **PowerShell**: `dcc-env -V` then `dcc-env -h` then `dcc-env --stock`
  **Git Bash**: `. dcc-env -V` then `. dcc-env --help` then `. dcc-env --stock; echo $?`

- [ ] **Expected:** `dcc-env 0.2.4` and `dcc-patcher 0.2.4` (no `these differ` line after HV.4); the help screen; `dcc-env: unknown option --stock (... --help lists the choices)` (Git Bash: `$?` is 2). Then `dcc-patcher status --brief`: no `DCC_MODE=-V`-style line (nothing was set).
- [ ] **Why this matters:** before 0.2.4, `dcc-env -h` and `-V` were stored as the mode.

## Section 1: help edge cases

### 1.1 Without dazzle-lib

- [ ] **Steps:** in a throwaway venv: `pip install <the 0.2.4 wheel>`, then `pip uninstall -y dazzle-lib`, then `dcc-patcher -h` and `dcc-patcher status`
- [ ] **Expected:** `-h` prints argparse's plain layout (no groups), exit 0; `status` works.

### 1.2 `use`'s wording

- [ ] **Steps:** `dcc-patcher -h`
- [ ] **Expected:** `use` reads "rebuilt when Claude Code or dcc-patcher changes"; nothing says "rebuilt on update".

## Section 2: update edge cases

### 2.1 Offline

- [ ] **Steps:** disconnect the network (or `dcc-patcher update` behind a blocked proxy)
- [ ] **Expected:** `PyPI: not reached (URLError: ...)`, one line; the rest of the report as usual.

### 2.2 No terminal

- [ ] **Steps:** `dcc-patcher update --fix < NUL` (cmd) / `dcc-patcher update --fix < /dev/null` (Git Bash)
- [ ] **Expected:** `dcc-patcher: no terminal to ask in; rerun with --yes, or run it yourself: ...`, exit 2, nothing run.

### 2.3 A wheel install (users' case)

- [ ] **Steps:** in a throwaway venv, `pip install dazzle-claude-code-patcher==0.2.3`, then `dcc-patcher update`
- [ ] **Expected:** 0.2.3 has no `update` command (`invalid choice`). After `pip install <0.2.4 wheel>`: `update` reports `(pip install)`, the scripts `[x] ... (dcc-env 0.2.4)`, and `up to date` unless PyPI has something newer.

## What the automated tests DON'T cover

- Real pip, real PyPI: every test uses a stub that installs nothing and no test goes online.
- The running-exe self-replace on a real install (measured once in a throwaway venv; HV.4 is the real one).
- How the help reads in your terminal's font and width.
- `dcc-env` from your real shells with the real dcc-patcher (the tests use a stub on a bare PATH).
