# Human Test Checklist: the launcher on PATH, `status`, and kept originals

**Target version:** 0.1.10
**Ships with commit:** TBD (v0.1.10)
**Companion automated tests:** 107 in total. New in this version: `tests/test_path.py` (9, run on a fake registry), `tests/test_originals.py` (3) and `tests/test_launcher.py` (+2). All 12 new behaviours were red-green audited: each test fails when its behaviour is reverted (`tests/one-offs/redgreen_v0.1.10.py`).

## What this is

The automated tests run `install-shim`, `uninstall-shim` and `status` against an in-memory registry and never touch the real `PATH`. That's deliberate, and it means everything that depends on Windows itself is untested until a person runs this:
- whether new shells really pick up the change;
- how cmd, PowerShell and Git Bash choose between `claude.cmd` and the extensionless `claude`;
- Windows Terminal;
- the y/N prompt;
- the first start after a real update.

The maintainer runs it on a real machine.

## Prerequisites

1. Windows, with Claude Code's native install at `%USERPROFILE%\.local\bin\claude.exe`, and dcc-patcher 0.1.10 installed (`dcc-patcher --version`).
2. **Back up your user environment before anything else.** This is the only real state this checklist changes.

   **cmd.exe**:
   ```cmd
   reg export HKCU\Environment "%TEMP%\dcc-env-backup.reg" /y
   ```
   **PowerShell**:
   ```powershell
   reg export HKCU\Environment "$env:TEMP\dcc-env-backup.reg" /y
   ```
   **POSIX (Git Bash)**:
   ```bash
   MSYS_NO_PATHCONV=1 reg export 'HKCU\Environment' "$TEMP/dcc-env-backup.reg" /y
   ```
3. Keep one terminal open from **before** the install all the way through. HV.2 needs a shell that predates the change.
4. **Don't run anything elevated** unless a step says so. The system `PATH` is only written when a system `claude` exists *and* the shell is elevated.

**Reset between sections:** `dcc-patcher uninstall-shim` (it removes only our entry), then `dcc-patcher status` should show `[ ] user PATH does not have ...`.

## High-Value Verification (~10 minutes)

### HV.1 -- a new shell runs the patched build

Validates: the user-PATH write plus the `WM_SETTINGCHANGE` broadcast reaching a newly started terminal. The PoC couldn't settle this.

- [ ] **Steps:**
  1. In your existing terminal: `dcc-patcher install-shim`, answer `y`.
  2. Open a **new** terminal from the Start menu or taskbar (not a new tab of an open Windows Terminal; that's HV.5).
  3. In it: `dcc-patcher status`.
- [ ] **Expected:**
  - Step 1 prints `user PATH updated (REG_SZ, <n> -> <n+len> chars, only our entry changed)` and the line for your current shell.
  - Step 3 shows `[x] claude -> ...\builds\bin\claude.cmd (the dcc-patcher shim; ...)` with the shim listed first, then `.local\bin\claude.exe`.
- [ ] **Why this matters:** this is the feature. If a new shell still finds stock, the broadcast didn't reach Explorer, and signing out and back in becomes the documented fallback.

### HV.2 -- the old shell is named, and one line fixes it

Validates: stale-shell detection and `shellenv`.

- [ ] **Steps:** in the terminal opened **before** HV.1:
  1. `dcc-patcher status`
  2. Run the line it prints after `->`, or `dcc-patcher shellenv`'s output.
  3. `dcc-patcher status` again.
- [ ] **Expected:** step 1 shows `[!] this shell started before that change` with a line for your shell:
  - cmd: `set "PATH=...;%PATH%"`
  - PowerShell: `$env:Path = "...;" + $env:Path`
  - Git Bash: `export PATH="/c/...:$PATH"`

  Step 3 shows `[x] claude -> ...claude.cmd`, and the `[!]` is gone.
- [ ] **Why this matters:** without it the user's current shell silently keeps running stock, and the only advice would be "open a new shell".

### HV.3 -- uninstall removes only our entry

Validates: the delta removal; nothing restored from a snapshot.

- [ ] **Steps:**
  1. Note the user PATH now (it should contain the shim folder).
  2. `dcc-patcher uninstall-shim`
  3. Compare the registry value with the value recorded before the install (any shell; run where `dcc_patcher` imports):
     ```
     python -c "import winreg,json;from dcc_patcher import builds;k=winreg.OpenKey(winreg.HKEY_CURRENT_USER,'Environment');v,t=winreg.QueryValueEx(k,'Path');b=json.load(open(builds.builds_dir()/'path.json'))['base_path_user'];print('identical' if v==b['value'] else 'DIFFERS', t, b['type'])"
     ```
- [ ] **Expected:** `user PATH: removed <folder> (only that entry)`, then `identical 1 REG_SZ`, or `2 REG_EXPAND_SZ` if that's what yours is. If another installer changed PATH in between, `DIFFERS` is right: its entry must still be there, with only ours gone.
- [ ] **Why this matters:** PATH is shared. Restoring a saved copy would delete other tools' entries.

### HV.4 -- which `claude` each shell picks (open question U3)

Validates: how cmd, PowerShell and Git Bash treat `claude.cmd` next to the extensionless POSIX `claude` in one folder.

- [ ] **Steps** (with the shim on PATH):
  - **cmd.exe:** `where claude`, then `claude --version`
  - **PowerShell:** `Get-Command claude -All`, then `claude --version`
  - **Git Bash:** `type -a claude`, then `claude --version`
- [ ] **Expected:**
  - cmd and PowerShell run `claude.cmd`; PowerShell must **not** offer to "open" the extensionless `claude` with an app.
  - Git Bash runs the extensionless `claude` (sh).
  - All three print `<version> + dcc 0.1.10 (Dazzle Claude Code)`.
- [ ] **Why this matters:** if PowerShell picks the extensionless file, Windows' shims need their own folder. That's the fallback named in the design.

### HV.5 -- a Windows Terminal new tab

Validates: open question U2. Windows Terminal keeps its own environment.

- [ ] **Steps:** with Windows Terminal already running **from before HV.1**, open a new tab, then `dcc-patcher status`.
- [ ] **Expected:** either `[x] claude -> ...claude.cmd` (Windows Terminal reloads the environment for new tabs), or `[!] this shell started before that change`. Either result is acceptable; **record which**, because it decides what the README tells users.
- [ ] **Why this matters:** Windows Terminal is where most users will try it first.

### HV.6 -- the first start after an update says so up front

Validates: the rebuilding line.

- [ ] **Steps:** after Claude Code next updates itself, type `claude` in a shell where the shim is first.
- [ ] **Expected:** at once, `dcc: Claude Code changed; building the patched copy... `. A few seconds later the same line ends with `done; now running claude-dcc-<new>+dcc0.1.10.exe`, and Claude Code starts. Then `dcc-patcher status` shows `[x] <n> kept` under Originals, including the new version.
- [ ] **Why this matters:** a silent pause of a few seconds on every update looks like a hang.

## Section 1: install-shim edge cases

### 1.1 Declining

- [ ] **Steps:** `dcc-patcher uninstall-shim`, then `dcc-patcher install-shim` and answer `n`.
- [ ] **Expected:** `user PATH left as it was`, exit code 1, and `status` still shows `[ ] user PATH does not have ...`.

### 1.2 Running it twice

- [ ] **Steps:** `dcc-patcher install-shim --yes` twice.
- [ ] **Expected:** the second run says `user PATH: already has <folder> ahead of <...>\.local\bin` and writes nothing.

### 1.3 Our entry moved behind `.local\bin` by hand

- [ ] **Steps:** in System Properties, Environment Variables, move the shim folder below `.local\bin`. Then `dcc-patcher status`, then `dcc-patcher install-shim --yes`.
- [ ] **Expected:** `status` shows `[!] user PATH has <folder>, but behind ...`. The install moves it just ahead of `.local\bin`, and nothing else moves.

### 1.4 From a script (no terminal attached)

- [ ] **Steps:** `echo n | dcc-patcher install-shim` (cmd, PowerShell and Git Bash alike).
- [ ] **Expected:** `PATH not changed (not an interactive shell)... dcc-patcher install-shim --yes`. PATH is unchanged.

### 1.5 `--no-path`

- [ ] **Steps:** `dcc-patcher install-shim --no-path`
- [ ] **Expected:** the shims are written and PATH isn't touched; the old instruction line is printed.

### 1.6 The system PATH (skip unless a system `claude` exists)

`status` shows `[x] system PATH has no claude of its own` on most machines; if so, skip this section. If it shows `[ ] system PATH has <file>, which always wins`:

- [ ] **Steps:**
  1. Back up the system environment from an **elevated** shell: `reg export "HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\Environment" "%TEMP%\dcc-sysenv-backup.reg" /y`.
  2. In that elevated shell: `dcc-patcher install-shim`, and answer `y` to the system question.
- [ ] **Expected:**
  - The shims are copied to `%ProgramFiles%\dazzle-claude-code-patcher\bin` (only admins can write there);
  - that folder sits just before the folder holding the system `claude`;
  - the system PATH keeps `REG_EXPAND_SZ` and its `%SystemRoot%` entries unexpanded;
  - `private\builds\bin` never appears in the system PATH.

## Section 2: status

### 2.1 Exit code

- [ ] **Steps:** `dcc-patcher status`, then the exit code: `echo %ERRORLEVEL%` (cmd), `$LASTEXITCODE` (PowerShell), `echo $?` (POSIX).
- [ ] **Expected:** 0 when every item is `[x]` or `[~]`; 1 while any `[ ]` or `[!]` remains.

### 2.2 Reading it

- [ ] **Check:** is each line understandable without this checklist? Does every open item name the command that fixes it? Does it fit an 80-column terminal without confusing wraps? Note anything unclear.

## Section 3: originals

### 3.1 archive

- [ ] **Steps:** `dcc-patcher archive`, then again.
- [ ] **Expected:** the first run prints `kept <file> as claude-cc-<version>.exe` for anything new; the second prints `0 newly kept, <n> already kept`. The `.local\bin` folder is unchanged; compare the listings before and after: `dir %USERPROFILE%\.local\bin` / `Get-ChildItem $env:USERPROFILE\.local\bin` / `ls -la ~/.local/bin`.

### 3.2 After an update renames `claude.exe` to `.old`

- [ ] **Steps:** after an update, `dcc-patcher status` before starting `claude`.
- [ ] **Expected:** only the new `claude.exe` is listed as not kept. The renamed `.old` file is recognised as the build already kept (same size, time and file id).

## What the automated tests DON'T cover

- The real registry and the real broadcast; tests can't reach either, by design (HV.1, HV.3).
- How real shells resolve names, and the PowerShell extensionless-file behaviour (HV.4).
- Windows Terminal's environment handling (HV.5).
- The y/N prompt in a real terminal (1.1).
- Elevation and the system PATH on a real machine (1.6).
- A real update by Claude Code's updater (HV.6, 3.2).
- Whether `status` reads well (2.2).

## Reporting issues found

Note the step, the exact command and output, and the output of `dcc-patcher status`. Attach `path-log.jsonl` from the builds folder if PATH is involved; remove anything private first. File it against #9.

## Cleanup

1. `dcc-patcher uninstall-shim` if you don't want to keep the shim on PATH.
2. If PATH looks wrong in any way, restore the backup:
   - cmd: `reg import "%TEMP%\dcc-env-backup.reg"`
   - PowerShell: `reg import "$env:TEMP\dcc-env-backup.reg"`
   - Git Bash: `MSYS_NO_PATHCONV=1 reg import "$TEMP/dcc-env-backup.reg"`

   Then sign out and back in. **This restores the whole user environment as it was before HV.1**, including anything else changed since, so use it only if something went wrong.
3. Elevated runs only: restore `dcc-sysenv-backup.reg` the same way, from an elevated shell, if needed.
