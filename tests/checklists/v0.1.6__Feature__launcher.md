# Human Test Checklist: the launcher, so the patched build is just `claude` (#5)

**Target version:** 0.1.6
**Ships with commit:** v0.1.6: a launcher, so the patched build is just claude (#5)
**Companion automated tests:** 81 in the suite, including 18 in `tests/test_launcher.py` (every launch is stubbed). Mutation: 18 of 22 killed, 4 equivalent or don't-care (`tests/mutation/v0.1.6__sweep__launcher.md`).

## What this is

`dcc-patcher install-shim` writes `claude` and `claude-stock` launchers. `claude` runs the current patched build, rebuilds it when the official `claude.exe` updates, and falls back to stock with one line when a patch needs attention. The automated tests never launch anything. This checklist covers what only a real shell can show: which `claude` each shell finds, whether arguments, exit codes and Ctrl+C pass through, and how a real update is handled. djdarcy runs it.

## Prerequisites

1. Windows; Claude Code at `%USERPROFILE%\.local\bin\claude.exe`; this repo installed editable (`pip install -e .`).
2. **Use a scratch builds folder first** (sections 1–3), so your real state isn't touched:
   - **cmd.exe:** `set DCC_BUILDS_DIR=%TEMP%\dcc-launch-test`
   - **PowerShell:** `$env:DCC_BUILDS_DIR = "$env:TEMP\dcc-launch-test"`
   - **POSIX (Git Bash):** `export DCC_BUILDS_DIR="$TEMP/dcc-launch-test"`
3. Put the shim folder on `PATH` **for this terminal only**, ahead of `.local\bin`:
   - **cmd.exe:** `set PATH=%DCC_BUILDS_DIR%\bin;%PATH%`
   - **PowerShell:** `$env:PATH = "$env:DCC_BUILDS_DIR\bin;$env:PATH"`
   - **POSIX:** `export PATH="$DCC_BUILDS_DIR/bin:$PATH"`
4. Session runs use the test config (`python scripts/test_config.py env`), never a real session.

**Reset:** delete the scratch folder (cmd `rmdir /s /q %TEMP%\dcc-launch-test`, PowerShell `Remove-Item -Recurse -Force $env:TEMP\dcc-launch-test`, POSIX `rm -rf "$TEMP/dcc-launch-test"`).

## High-Value Verification (~10 minutes)

### HV.1 -- the shims are written, and each shell finds the right one

- [ ] **Steps:** `dcc-patcher install-shim`, then in each shell: cmd `where claude`; PowerShell `Get-Command claude -All`; Git Bash `type -a claude`. Also try `dz srch-path claude`.
- [ ] **Expected:** four files in `<scratch>\bin` (`claude`, `claude.cmd`, `claude-stock`, `claude-stock.cmd`). cmd and PowerShell resolve `claude` to `claude.cmd` first; Git Bash resolves it to the extensionless `claude`. `.local\bin\claude.exe` is listed after them.
- [ ] **Why this matters:** if a shell skips the shim, that shell silently runs stock.

### HV.2 -- the first start builds and runs the patched copy

- [ ] **Steps:** `claude --version` in cmd, PowerShell and Git Bash.
- [ ] **Expected:** the first run prints `dcc: Claude Code updated; now running claude-dcc-<cc>+dcc0.1.6.exe` to stderr after a few seconds, then `<cc> + dcc 0.1.6 (Dazzle Claude Code)`. Later runs print only the version, with no noticeable delay.

### HV.3 -- `claude-stock` and `DCC_MODE`

- [ ] **Steps:** `claude-stock --version`; then set `DCC_MODE=stock` for the shell (cmd `set DCC_MODE=stock`, PowerShell `$env:DCC_MODE="stock"`, POSIX `export DCC_MODE=stock`) and run `claude --version`; then set `DCC_MODE=vanilla` and run it again.
- [ ] **Expected:** `<cc> (Claude Code)` twice, then a one-line `DCC_MODE=vanilla is not stock or patched` followed by the patched version.

### HV.4 -- `use` and `rollback`

- [ ] **Steps:** `dcc-patcher use`; `dcc-patcher use stock`, then `claude --version`; `dcc-patcher use patched`; `dcc-patcher rollback`.
- [ ] **Expected:** the state is printed; stock runs after `use stock`; `rollback` says there's no older build (only one exists in the scratch folder) and exits 1.

### HV.5 -- arguments, exit codes and Ctrl+C pass through

- [ ] **Steps:** in the test config: `claude -p "say ok"` (then `echo %ERRORLEVEL%` / `$LASTEXITCODE` / `echo $?`); start `claude`, press Ctrl+C twice.
- [ ] **Expected:** the exit code is Claude Code's own. Ctrl+C reaches Claude Code. In cmd you may see `Terminate batch job (Y/N)?` after Claude exits, which is a `.cmd` habit; note it if it happens.

## Section 2: a real update (run when Claude Code next updates)

- [ ] After an update has replaced `.local\bin\claude.exe`, the first `claude` prints `now running claude-dcc-<new>+dcc...` and runs the new version. `dcc-patcher use` shows the new `current`, and the older build is still in the folder.
- [ ] If a patch no longer applies: one line, `dcc: patch <id> needs attention after the Claude Code update; running stock (...)`, then stock runs.
- [ ] `.local\bin` holds only the updater's own files (`claude.exe`, `claude.exe.old.*`). Neither the shims nor the builds folder were touched by the update.

## Section 3: the test config

- [ ] **Steps:** set the test config for this shell (cmd `set CLAUDE_CONFIG_DIR=%LOCALAPPDATA%\dazzle-claude-code-patcher\test-config`; PowerShell `$env:CLAUDE_CONFIG_DIR = "$env:LOCALAPPDATA\dazzle-claude-code-patcher\test-config"`; POSIX `export CLAUDE_CONFIG_DIR="$LOCALAPPDATA/dazzle-claude-code-patcher/test-config"`). Note `launcher.json`'s contents (cmd `type %DCC_BUILDS_DIR%\launcher.json`, PowerShell `Get-Content $env:DCC_BUILDS_DIR\launcher.json`, POSIX `cat "$DCC_BUILDS_DIR/launcher.json"`). Then, after an update, run `claude --version`.
- [ ] **Expected:** stock runs, after the "this is the test config" line. `launcher.json` and the builds folder's file list are unchanged.

## Section 4: the real install (when happy)

- [ ] Unset `DCC_BUILDS_DIR`, run `dcc-patcher install-shim` (it writes to `private\builds\bin`), and put that folder ahead of `.local\bin` in your user `PATH`. That `PATH` change is yours to make.

## What the automated tests DO cover

| Area | Count |
|---|---|
| the first start, unchanged starts (no re-hash), updates (including a same-size, same-mtime one), fallback and crash fallback | 6 |
| `DCC_MODE`, `use`, `rollback` (one step at a time), pinned builds | 5 |
| the test config writes nothing; nothing written into `.local\bin` or `~/.claude`; no official exe | 3 |
| `install-shim`: four files from two templates; refusals | 4 |

## What the automated tests DON'T cover

- How cmd, PowerShell, Git Bash and Windows Terminal resolve `claude` with both `claude` and `claude.cmd` in one folder.
- Real child-process behaviour: exit codes, Ctrl+C, the console, a running patched exe.
- The delay of the first start after an update (it patches 250 MB), and of a normal start (Python plus a stat).
- A real update by the native updater.

## Reporting issues found

Note the section and step, the shell, the exact command and its output (stdout and stderr), and `dcc-patcher use`'s output. File an issue referencing this checklist and v0.1.6.

## Cleanup

Delete the scratch folder (as in Reset). Unset the variables: cmd `set DCC_BUILDS_DIR=` and `set DCC_MODE=` and `set CLAUDE_CONFIG_DIR=`; PowerShell `Remove-Item Env:\DCC_BUILDS_DIR, Env:\DCC_MODE, Env:\CLAUDE_CONFIG_DIR`; POSIX `unset DCC_BUILDS_DIR DCC_MODE CLAUDE_CONFIG_DIR`. Then close the terminal so that its `PATH` change goes with it.
