# Human Test Checklist: dcc-patcher and the history-past-compaction patch

**Target version:** v0.2.0 (the commands first appear in v0.1.2 and v0.1.3)
**Ships with commit:** TBD (v0.1.3: patch specs, the engine, and check)
**Companion automated tests:** 45 tests:
- `tests/test_engine.py` (9)
- `tests/test_containers.py` (10)
- `tests/test_spec.py` (6)
- `tests/test_cli.py` (6)
- `tests/test_check.py` (4)
- `tests/test_containers_pe.py` (3)
- `tests/test_version.py` (7, the project template's version checks)

The real-build tests are skipped when `~/.local/bin/claude.exe` is absent.

## What this is

The automated suite proves the patcher's logic in memory and on a tiny synthetic executable. It never runs a patched Claude Code: the person running the patcher does that. This checklist covers what only a real run can show:
- the patched `claude-dcc.exe` starts;
- Bun really compiles the edited module;
- resuming a session scrolls back past its compactions;
- the model is sent exactly what stock Claude Code sends.

It also walks each command once by hand, for output a person has to read.

**The build to test is the one the spec produces** (`dcc-patcher apply`), not the proof of concept's earlier build. They do the same thing, but their JavaScript differs in two places:
- the crossing helper checks the row type itself;
- the walker edit no longer guards the call.

So a pass recorded against the proof-of-concept build does not carry over.

## Prerequisites

1. **Windows, with Claude Code's native build installed** at `%USERPROFILE%\.local\bin\claude.exe` (2.1.289 for the expected outputs below). Older builds saved beside it as `claude.exe.old.*` make Section 2 more useful.
2. **Python 3.11 or newer**, run from the repository root: every `python -m dcc_patcher` command assumes the current directory is the repo.
3. **Never point `-o` at the installed `claude.exe`.**
   - The patcher refuses to write over its input. Even so, keep every output under `build-out\`, which git ignores.
   - Nothing here changes the installed Claude Code or its updater.
4. **Session tests run in a throwaway config folder, never in `~/.claude`.**
   - `scripts/test_config.py` keeps one at `%LOCALAPPDATA%\dazzle-claude-code-patcher\test-config`.
   - `python scripts/test_config.py env` prints the two variables that select it: `CLAUDE_CONFIG_DIR` and `DISABLE_AUTOUPDATER=1`. Set them in the terminal used for HV.4/HV.5.
   - Log in once inside it: start `claude` with them set, then `/login`. The login stays in that folder.
   - `python scripts/test_config.py copy <session .jsonl>` copies a real session into it under a new id. The original is only read.
   - A test run there sees none of your user-level settings, skills or plugins, and nothing it writes reaches a real session. The folder you run it from still contributes its project-level `CLAUDE.md` and `.claude\settings*.json`, because those come from the working directory, not the config folder.
   - Run the patched and the stock side of a comparison from the same folder, against the same Claude Code release. Rebuild after every update.
5. **Antivirus and SmartScreen may react to an unsigned exe.** The patched copy has its Authenticode signature removed, because any edit invalidates it. If Windows blocks it, record exactly what was shown (Section 4.3).

**Reset between sections:** delete `build-out\` (it holds only outputs of this checklist).

- **cmd.exe:** `if exist build-out rmdir /s /q build-out`
- **PowerShell:** `if (Test-Path build-out) { Remove-Item -Recurse -Force build-out }`
- **POSIX (Git Bash):** `rm -rf build-out`

## High-Value Verification (~10 minutes)

If any of these fail, the work did not ship. Each one is covered in more detail below.

### HV.1 -- `check` says the history patch applies to your build (AC1)

- [ ] **Steps** (same in every shell):
  ```
  python -m dcc_patcher check %USERPROFILE%\.local\bin\claude.exe
  ```
  In PowerShell use `$env:USERPROFILE\.local\bin\claude.exe`; in Git Bash use `~/.local/bin/claude.exe`.
- [ ] **Expected:**
  - a line `2.1.289  <path>`;
  - `H  applies`;
  - six edit lines, each `APPLIES`: five `x1` and one `x2` (the pre-parse pair);
  - exit code 0.
- [ ] **Why this matters:** this is the one command you run after every Claude Code update. If it is wrong, nothing downstream can be trusted.

### HV.2 -- `apply` builds the patched copy

- [ ] **Steps:**
  ```
  python -m dcc_patcher apply %USERPROFILE%\.local\bin\claude.exe -o build-out\claude-dcc.exe
  ```
- [ ] **Expected:**
  - The same six `APPLIES` lines as HV.1.
  - Then `wrote <repo>\build-out\claude-dcc.exe` and, on the next line, `and <repo>\build-out\claude-dcc.exe.dcc-lock.json`: absolute paths since v0.1.5. Exit 0.
  - Without `-o` (v0.1.5), the build goes to the builds folder under both versions' names, with `claude-dcc.exe` pointing at it. `v0.1.5__Feature__versioned-builds.md` covers that.
  - The new exe is a little larger than the original, because the edited module source is appended.
- [ ] **Why this matters:** everything below runs this file.

### HV.3 -- the patched copy starts (AC6)

- [ ] **Steps:**
  ```
  build-out\claude-dcc.exe --version
  ```
- [ ] **Expected:**
  - `2.1.289 + dcc <this tool's version> (Dazzle Claude Code)`, e.g. `2.1.289 + dcc 0.1.3 (Dazzle Claude Code)`. The version-label patch (V) writes this, so the build says what it is; stock `claude --version` still says `2.1.289 (Claude Code)`.
  - No error, no stack trace, and no noticeable delay compared with `claude --version`.
- [ ] **Why this matters:** this proves Bun accepted the rewritten executable and compiled the edited module from source.

### HV.4 -- a resumed session scrolls back past its compactions (AC7, part 1)

- [ ] **Steps:**
  1. Pick a session that has been compacted at least once (long sessions usually have).
  2. Copy it into the test config (Prerequisite 4):
     ```
     python scripts\test_config.py copy %USERPROFILE%\.claude\projects\<project folder>\<session id>.jsonl
     ```
     Note the new id it prints.
  3. In a terminal with the test config's variables set, `cd` to the folder the session was started in. Claude Code finds a session through the project folder for the current directory.
  4. Resume the copy: `<repo>\build-out\claude-dcc.exe --resume <new id>`
  5. Press `Ctrl+O`, then `Ctrl+Home`.
- [ ] **Expected:**
  - the view reaches the session's **first** prompt, before every compaction;
  - the compaction summaries appear between the older parts;
  - no part of the conversation shows twice.
- [ ] **Why this matters:** this is the bug the patch fixes. Stock Claude Code stops at the last compaction.

### HV.5 -- the model is sent the same request as stock (AC7, part 2)

- [ ] **Steps:**
  1. Make a second copy of the same original session (step 2 of HV.4 again).
  2. Send one identical short prompt (`say ok`) in each copy, both with the test config's variables set:
     - in the HV.4 copy, through `claude-dcc.exe`;
     - in the second copy, through stock `claude --resume <second id>`.

     The patched build must come from the same Claude Code release as stock `claude`; rebuild after an update.
  3. Compare, in the same terminal:
     ```
     python scripts\compare_usage.py <copy 1 id> <copy 2 id>
     ```
     A bare session id is looked up in the config folder's projects (the test config when `CLAUDE_CONFIG_DIR` is set); pass the full `.jsonl` path if it is ambiguous.
- [ ] **Expected:**
  - The two request totals agree within 0.1%. Measured results:
    - the proof of concept: 527,575 vs 527,509 (2.1.289, full user config);
    - the tool's build: 563,935 patched vs 563,939 stock (2.1.290, test config, 2026-10-05), with identical cache reads of 534,231.
  - The totals don't shrink in the test config. The folder the session runs in still contributes its project settings and `CLAUDE.md` (for `~/.claude`, its own `CLAUDE.md` and `.claude\settings.local.json`). That's fine, because both runs load the same ones.
  - Whichever ran second shows a large cache read, because the first one wrote the same prefix.
  - Neither copy compacted.
- [ ] **Why this matters:** the patch must change what you can **see**, never what the model **receives**. A larger total means older history is being sent, and that costs money.

### HV.6 -- applying twice does nothing (AC4)

- [ ] **Steps:**
  ```
  python -m dcc_patcher apply build-out\claude-dcc.exe -o build-out\again.exe
  ```
- [ ] **Expected:**
  - `H  already-applied  (signature /*dazzle-claude-code:history-v1*/ present)`;
  - `nothing to apply; nothing written`, exit 0;
  - no `build-out\again.exe`.
- [ ] **Why this matters:** re-running the patcher, by hand or from a script, must never stack a second copy of the patch.

## Section 1: The commands, read by a person (~10 min)

### 1.1 `--help` lists every command

- [ ] **Steps:** `python -m dcc_patcher --help`
- [ ] **Expected:**
  - `inspect`, `validate`, `check` and `apply` are listed, each with a one-line description.
  - The description says what the tool is for.
- [ ] **Check:** each subcommand's `--help` reads clearly, e.g. `python -m dcc_patcher apply --help`, and `-o` says it is never the input.

### 1.2 `inspect` describes a build

- [ ] **Steps:** `python -m dcc_patcher inspect %USERPROFILE%\.local\bin\claude.exe --marker tengu_chain_parent_cycle`
- [ ] **Expected:**
  - `format: pe`, `version: 2.1.289`, a module count in the thousands, and `flags: 0x1bff`;
  - one `marker:` line naming a `chunk-*.js` module with its source and bytecode sizes.

### 1.3 `inspect` refuses a file that isn't a Windows Bun executable (AC11)

- [ ] **Steps:** `python -m dcc_patcher inspect README.md`
- [ ] **Expected:** one line `dcc-patcher: unsupported format: unknown (...)`, exit 2, no traceback.
- [ ] **Check the exit code:**
  - **cmd.exe:** `echo %ERRORLEVEL%`
  - **PowerShell:** `$LASTEXITCODE`
  - **POSIX:** `echo $?`

### 1.4 `validate` accepts the bundled patch and names a mistake

- [ ] **Steps:**
  1. `python -m dcc_patcher validate` should print `ok  H  History past compaction  (6 edits)  <path>`, exit 0.
  2. Make a broken copy.
     - **cmd.exe:** `copy patches\H-history-past-compaction\patch.toml %TEMP%\bad.toml`
     - **PowerShell:** `Copy-Item patches\H-history-past-compaction\patch.toml $env:TEMP\bad.toml`
     - **POSIX:** `cp dcc_patcher/patches/H-history-past-compaction/patch.toml /tmp/bad.toml`

     Then edit the copy and change one `@@e@@` to `@@nope@@`.
  3. `python -m dcc_patcher validate %TEMP%\bad.toml`
- [ ] **Expected (step 3):** `... @@nope@@ is not captured by this or an earlier edit`, exit 2. The message names the edit by number and name.

## Section 2: Across builds (~5 min)

### 2.1 `check` across every saved build (AC2)

- [ ] **Steps:**
  - **cmd.exe:** `python -m dcc_patcher check "%USERPROFILE%\.local\bin\claude.exe*"`
  - **PowerShell:** `python -m dcc_patcher check "$env:USERPROFILE\.local\bin\claude.exe*"`
  - **POSIX:** `python -m dcc_patcher check ~/.local/bin/claude.exe*`
- [ ] **Expected:**
  - One block per build, oldest first, each with its version.
  - On 2.1.278 through 2.1.289, every edit `APPLIES`, exit 0.
  - On any build where an edit does not apply: the edit names itself (`MISSING` / `AMBIGUOUS` / `LANDMARK-GONE`), the exit code is 1, and there is no traceback.
- [ ] **Check:**
  - In cmd.exe the quoted wildcard is not expanded by the shell; the tool expands it itself.
  - A wildcard that matches nothing gives `no files matched`, exit 2.

### 2.2 A baseline for later diagnosis

- [ ] **Steps:** `python -m dcc_patcher check %USERPROFILE%\.local\bin\claude.exe --lock-out build-out\locks`
- [ ] **Expected:** `build-out\locks\2.1.289.dcc-lock.json` exists. It holds each edit's matched text (`before`) and replacement (`after`).
- [ ] **Later, when an update breaks an edit:**
  - run `python -m dcc_patcher check <new claude.exe> --baseline build-out\locks\2.1.289.dcc-lock.json`;
  - the failing edit should show a short diff in which renamed variables appear as `_` and only real code changes are marked.

  Record whether the diff was enough to fix the pattern.

## Section 3: Fail-safe behaviour (~5 min)

### 3.1 `apply` never writes over its input

- [ ] **Steps:**
  1. `copy %USERPROFILE%\.local\bin\claude.exe build-out\stock.exe` (PowerShell: `Copy-Item`; POSIX: `cp`)
  2. `python -m dcc_patcher apply build-out\stock.exe -o build-out\stock.exe`
- [ ] **Expected:** `refusing to write over the input; give a different -o`, exit 2. `stock.exe` is unchanged.

### 3.2 The lockfile matches the output

- [ ] **Steps:** after HV.2, compare `output_sha256` in `build-out\claude-dcc.exe.dcc-lock.json` with the file's hash.
  - **cmd.exe:** `certutil -hashfile build-out\claude-dcc.exe SHA256`
  - **PowerShell:** `(Get-FileHash build-out\claude-dcc.exe).Hash.ToLower()`
  - **POSIX:** `sha256sum build-out/claude-dcc.exe`
- [ ] **Expected:** they are equal. The same holds for `input_sha256` against the installed `claude.exe`.

## Section 4: Running the patched copy (~10 min)

### 4.1 Normal use is unaffected

- [ ] Start `build-out\claude-dcc.exe` in a scratch folder.
- [ ] Ask one question, run one tool, and exit.
- [ ] **Expected:** behaves exactly like stock, with no extra output.

### 4.2 Startup time

- [ ] Time `--version` and a resume, patched vs stock, three runs each.
  - **PowerShell:** `Measure-Command { build-out\claude-dcc.exe --version }`
- [ ] **Expected:**
  - The patched copy compiles one module from source at startup, so a small extra delay is normal.
  - Record the numbers. More than about half a second extra on a resume is worth reporting.

### 4.3 Windows' reaction to an unsigned exe

- [ ] **Expected:** it runs from a terminal.
- [ ] If SmartScreen, Defender or another antivirus warns, blocks or quarantines it, record:
  - the product;
  - the exact message;
  - whether allowing it once was enough.

### 4.4 The debug build (optional)

- [ ] **Steps:**
  1. `python -m dcc_patcher apply %USERPROFILE%\.local\bin\claude.exe -o build-out\claude-dcc-debug.exe --debug`
  2. Resume a session **copy** with that exe.
- [ ] **Expected:**
  - A log named `dcc-debug.log` appears in the directory you started it from, or at the path in `DZ_DEBUG_LOG` if set.
  - It contains `module loaded` and `walk: boundary ...` lines, one per compaction crossed.
- [ ] **Set the log path first** (optional):
  - **cmd.exe:** `set DZ_DEBUG_LOG=%TEMP%\dcc-debug.log`
  - **PowerShell:** `$env:DZ_DEBUG_LOG = "$env:TEMP\dcc-debug.log"`
  - **POSIX:** `export DZ_DEBUG_LOG=/tmp/dcc-debug.log`

## What the automated tests DO cover

| Area | Test file | Count |
|---|---|---|
| Format detection and refusal (ELF, Mach-O, unknown) | `tests/test_containers.py` | 10 |
| PE rewrite and verify on the real build, in memory | `tests/test_containers_pe.py` | 3 |
| Spec loading and author mistakes | `tests/test_spec.py` | 6 |
| Engine: fail closed, idempotent (also when an edit removes its own marker), a patch over two modules, upstream-fixed, per-site names, the real build | `tests/test_engine.py` | 9 |
| `check`: region diff against a baseline, renames (including spreads) not shown as changes, several files, real build | `tests/test_check.py` | 4 |
| `inspect` and `validate` exit codes; a mistyped path is a message, not a traceback | `tests/test_cli.py` | 6 |

## What the automated tests DON'T cover

- **Bun actually running the edited module.** Every test stops at "the image verifies"; HV.3 and HV.4 are the only proof it runs.
- **What the model receives** (HV.5). The suite cannot make an API call.
- **Scrolling in the real terminal UI**, with Ctrl+O and Ctrl+Home.
- **Signature removal:** SmartScreen, Defender, other antivirus, and corporate policy.
- **Startup cost** of compiling one module from source.
- **The debug log's location** when started from different directories.
- **Readability of the region diff** on a real upstream change. It was previewed only on a simulated one.
- **Builds newer than 2.1.289** and non-Windows systems (refused by design today).

## Reporting issues found

1. Note the section and step number.
2. Capture the exact command and its full output, including the exit code.
3. For HV.4/HV.5, keep both session copies and the `.dcc-lock.json`.
4. File an issue referencing this checklist and the Claude Code version.

## Cleanup

- [ ] Delete `build-out\` (see Prerequisites).
- [ ] Nothing to clean in `~/.claude`: the session copies live in the test config.
  - `python scripts/test_config.py list` shows them.
  - Keep them for the next run, or stage the whole folder with `dz safedel -r <folder>`. That also removes its login.
- [ ] If a test copy was ever made in `~/.claude` (for instance with `copy_session.py` alone), move it, and everything resuming it left behind, into the test config:

  ```
  python scripts/test_config.py move-in <id>
  ```

  - `move-back` undoes that.
  - `move-in` only accepts an id that starts with `dcc0dcc0-` (every copy since 2026-10-05 ~15:40 is marked that way) or one in the test config's ledger.
  - For an older or hand-made copy, enter it first: `python scripts/test_config.py record <id> "<what it was copied from>"`.
  - This is deliberate: a fork or branch Claude Code made looks just like a copy from outside, and must never be moved.
- [ ] Close the terminal that had the test config's variables set, or unset them:
  - **cmd.exe:** `set CLAUDE_CONFIG_DIR=` and `set DISABLE_AUTOUPDATER=`
  - **PowerShell:** `Remove-Item Env:\CLAUDE_CONFIG_DIR, Env:\DISABLE_AUTOUPDATER`
  - **POSIX:** `unset CLAUDE_CONFIG_DIR DISABLE_AUTOUPDATER`
- [ ] Unset `DZ_DEBUG_LOG` if you set it:
  - **cmd.exe:** `set DZ_DEBUG_LOG=`
  - **PowerShell:** `Remove-Item Env:\DZ_DEBUG_LOG`
  - **POSIX:** `unset DZ_DEBUG_LOG`
