# Human Test Checklist: plugins see every patch a build carries (`DCC_PATCHES`, `DCC_PATCHER`)

**Target version:** v0.2.3
**Ships with commit:** v0.2.3: plugins see every patch a build carries (DCC_PATCHES, DCC_PATCHER); stock inherits no stale signal
**Companion automated tests:** 132 in the suite. New for this version: `tests/test_launcher.py` (1: the launcher sets the two variables for a patched build and strips every signal variable for stock; an anchor for the strip, a fence for the set). Red-green: `tests/one-offs/redgreen_v0.2.2.py`, mutations c and d.

## What this is

When the launcher starts a patched build it now sets two environment variables from the build's lockfile: `DCC_PATCHES` (every patch id with its tag) and `DCC_PATCHER` (the version that made the build). When it starts stock, it removes those two and every `DCC_PATCH_*` it inherited, so a stock Claude Code started from inside a patched session's shell no longer carries a signal that isn't true of it. The history patch's own `DCC_PATCH_H` stays as it was. Plugins read all three with `$.env.get`. The automated test proves the launcher's two branches on a fake world; it cannot show the read from inside a plugin hook or the inheritance through real shells. A person does that here, with a plugin that prints the variables (claude-bookmarks 0.1.7's `/bm-env` does).

## Prerequisites

1. dcc-patcher v0.2.3 set up (`dcc-env`), Windows, Claude Code 2.1.278 or later, a patched build current (`dcc-patcher use` shows it).
2. A plugin that prints the variables. claude-bookmarks 0.1.7 or later: `/bm-env` prints `dcc-patcher: <version or "none seen">; DCC_PATCH_H=...; DCC_PATCHES=...`. Any plugin with `$.env.get` and a toast will do.
3. **State isolation:** nothing here writes to `~/.claude` or a session file; the variables live in each process. `dcc-env stock` is undone by `dcc-env default`.
4. Seen live already (2026-10-09, before this version): `/bm-env` on stock printed `none seen; DCC_PATCH_H=(unset); DCC_PATCHES=(unset)`; on a patched 0.2.2 process started before this change it printed `none seen; DCC_PATCH_H=history-v1; DCC_PATCHES=(unset)`, which is the state this version replaces.

## High-Value Verification (~5 minutes)

**If you only have 5 minutes**, run these four.

### HV.1 — A fresh patched start carries the full signal

Validates: `DCC_PATCHES` and `DCC_PATCHER` are set from the lockfile at start.

- [ ] **Steps:** open a new window from the Start menu, `claude`, then `/bm-env` (or your plugin's print).
- [ ] **Expected:** `dcc-patcher: v0.2.3; DCC_PATCH_H=history-v1; DCC_PATCHES=B=banner-label-v1,B2=banner-label-flicker-free-v1,H=history-v1,J=cross-file-v1,R=rows-v1,V=version-label-v1` (the plugin's exact wording may differ; the three values are what matter).
- [ ] **Why this matters:** this is what lets a plugin gate each capability on the patch that provides it.

### HV.2 — Stock started from inside a patched session carries nothing

Validates: the strip. Before this version, a stock Claude Code started from a patched session's shell inherited `DCC_PATCH_H=history-v1`.

- [ ] **Steps:** inside the patched session from HV.1, open a shell the session owns (its Bash tool, or a terminal started from it), then:

  **cmd.exe**:
  ```cmd
  echo %DCC_PATCH_H%
  claude-stock
  ```

  **PowerShell**:
  ```powershell
  $env:DCC_PATCH_H
  claude-stock
  ```

  **POSIX (Git Bash)**:
  ```bash
  echo $DCC_PATCH_H
  claude-stock
  ```
  In the stock Claude Code that opens, `/bm-env`.
- [ ] **Expected:** the shell prints `history-v1` (it inherited it); the stock session's `/bm-env` prints all three unset (`none seen; DCC_PATCH_H=(unset); DCC_PATCHES=(unset)`).
- [ ] **Why this matters:** a plugin on stock must not believe it has the patched reach.

### HV.3 — Stock from a Start-menu shell

- [ ] **Steps:** a new window from the Start menu, `claude-stock`, `/bm-env`.
- [ ] **Expected:** all three unset. (Nothing to strip here; the point is that the result is the same as HV.2.)
- [ ] **Why this matters:** the common case stays trivially right.

### HV.4 — A child of the patched session sees the variables

Validates: the variables reach child processes (tools, MCP servers), as the README says.

- [ ] **Steps:** in the patched session's shell tool:

  **cmd.exe**: `echo %DCC_PATCHES% & echo %DCC_PATCHER%`
  **PowerShell**: `$env:DCC_PATCHES; $env:DCC_PATCHER`
  **POSIX**: `echo "$DCC_PATCHES"; echo "$DCC_PATCHER"`
- [ ] **Expected:** the six-patch list and `0.2.3`.
- [ ] **Why this matters:** an MCP server or a tool can key on them too.

## Section 1: Edges (~3 min)

### 1.1 A build run directly, without the launcher

- [ ] **Steps:** run the build by path (`<builds>\claude-dcc-<cc>+dcc0.2.3.exe`), then `/bm-env`.
- [ ] **Expected:** `DCC_PATCH_H=history-v1` (the patch sets it itself) but `DCC_PATCHES` unset and `none seen` (those two are the launcher's). Documented behaviour.

### 1.2 A pinned older build

- [ ] **Steps:** `dcc-patcher use claude-dcc-2.1.295+dcc0.1.11.exe`, `claude`, `/bm-env`, then `dcc-patcher use patched`.
- [ ] **Expected:** `DCC_PATCHER=0.1.11` and that build's own lockfile set (no `R=rows-v1`, since R arrived in 0.2.2). The signal describes the build that runs, not the installed tool.

### 1.3 A build whose lockfile is missing

- [ ] **Steps:** with a copy of a build in the builds folder whose `.dcc-lock.json` is absent, `dcc-patcher use <that file>`, `claude --version`, then `dcc-patcher use patched`.
- [ ] **Expected:** it starts normally; `DCC_PATCHES`/`DCC_PATCHER` unset; no error line.

## What the automated tests DON'T cover

- **The read from inside a plugin hook** (`$.env.get` in Claude Code's worker): only a real plugin shows it.
- **Inheritance through real shells**: a cmd/PowerShell/Git Bash started by the session, then `claude-stock` from it.
- **The plugin's wording** of what it prints.

## Reporting issues found

1. Note the step and the shell.
2. Capture `/bm-env`'s line and `dcc-patcher use`.
3. File an issue referencing this checklist and v0.2.3; for the signal itself, #8.
